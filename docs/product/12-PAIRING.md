# 12 — Pairing devices into the fabric

Pairing is the bootstrap moment when a new device becomes a node in
the user's Jessica fabric. It happens exactly once per device and
establishes:

1. The **fabric identity** (shared symmetric key + fabric UUID).
2. The new device's **identity keypair** (Ed25519; private key stays
   on-device).
3. The new device's **role** + initial offered capabilities.
4. An initial **sync log replay** so the new device knows everything
   the fabric already knows.

## 1. Threat model

The pairing channel must defeat:

- **Eavesdropping** on the LAN.
- **Active MITM** — a malicious device claiming to be the new device
  or to be the existing fabric.
- **Replay** — a device replaying old pairing exchanges.

The shared-secret confirmation step is what protects against MITM —
a passive attacker can't recover it from the channel; an active
attacker can intercept but can't produce the right confirmation
without knowing the user-spoken code.

## 2. Pairing methods

Two methods, picked by what's available:

### A. QR code (mobile ↔ Pi or mobile ↔ mobile)

1. The user opens "Settings → Pairing" on the existing node and taps
   "Pair a new device". The existing node displays a QR encoding:
   `jessica-pair://<fabric_id>?token=<one-time>&relay=<addr>`.
   The token is a 32-byte random value valid for 5 minutes.
2. On the new device the user taps "Join existing Jessica" and
   scans the QR.
3. New device connects (LAN-direct over mDNS or via the relay) and
   sends `pair.request` with its public key + a derived hmac proving
   it has the token.
4. Existing node verifies the hmac, replies with `pair.challenge`
   containing a fresh 6-word phrase (e.g. "pies-pingwin-pomidor-
   pajak-piorun-piwo") it speaks aloud OR shows on screen.
5. The user **says the phrase to both devices**. Both record + send
   `pair.confirm` (with a TTS-resilient transcript) to each other.
6. If transcripts match (Levenshtein ≤ 1), the existing node
   transmits the fabric symmetric key + the current sync log head
   to the new device over the secure channel.
7. Both devices broadcast `fabric.peer_introduced` to the sync log.
8. Done.

### B. Voice-spelled code (Pi has no screen / no camera)

Same as method A but the QR step is replaced by:

1. The user says on the existing Pi: "Jess, sparuj nowe urządzenie."
2. Pi speaks: "Powiedz w telefonie: dołącz do fabric — kod
   pies-pingwin-pomidor."  (Three words from the secret table —
   second half stays on Pi for confirmation.)
3. The user says on the phone: "Jess, dołącz do fabric — kod
   pies-pingwin-pomidor."
4. Phone broadcasts the partial code; Pi recognises it.
5. Pi then says the second half: "Drugi kod: pajak-piorun-piwo."
6. The user repeats on the phone.
7. Phone sends `pair.confirm`; Pi accepts.
8. Sync key + log head transmitted; pairing complete.

The split-code design keeps the channel safe even if an attacker
hears the first three words via room audio leak — they still need
the second three.

### Code generation

- 6 words from a curated 256-word dictionary (PL + EN both supported,
  picked per the active language at pairing time).
- Words chosen for **phonetic distinctness** (no homophones, no
  borrowings that conflict).
- The same dictionary in `assets/pairing-dict-pl.txt` and
  `assets/pairing-dict-en.txt` is used by both implementations.

## 3. Identity keys

Each device generates an **Ed25519** keypair on first run. The
private key never leaves the device's secure storage:

- Pi: `/var/lib/blazen/identity/private.key`, mode `0400`,
  `chattr +i` if possible.
- iOS: Keychain Services with `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`.
- Android: Keystore + biometric-bound access.

Public keys are exchanged during pairing and stored in the sync log
as `fabric.peer_introduced` facts.

## 4. Fabric symmetric key

A 32-byte ChaCha20-Poly1305 key generated by the first device when
the fabric is first created (i.e., on the very first device's first
boot). Every subsequent pairing transmits this key to the new device
inside the secure pair channel.

This key encrypts:

- All sync log entries at rest.
- All RPC payloads (on top of the per-connection TLS).
- The bundled exports a user creates via "Jess, daj mi wszystko"
  (so the export is portable to a future fabric without leaking
  things to the recipient if shared accidentally).

It does **not** encrypt:

- mDNS announcements (they only carry fabric ID and device kind,
  no secrets).
- OS-level secrets (those use OS-provided storage).

The user can rotate the key with "Jess, wymień klucz fabric" (loud-
confirm) — every node receives the new key on next contact and
re-encrypts its local log.

## 5. Pair flow details

```
existing node A                            new node B
      │                                          │
      │  user: "Jess, sparuj nowe urządzenie"     │
      │                                          │
      │  A: opens UI, shows QR with token T       │
      │  (or speaks first 3 words of code C)      │
      │                                          │
      │            (user scans QR / repeats code) │
      │                                          │
      │ ◀────── pair.request {pubkey_B, hmac(T)}  │
      │                                          │
      │ verify hmac; pick challenge C; speak it   │
      │                                          │
      │ ───── pair.challenge {C, sig_A} ─────▶    │
      │                                          │
      │  user says C on both → ASR transcripts   │
      │                                          │
      │ ◀──── pair.confirm {asr_B} ──────────    │
      │ ──── pair.confirm {asr_A} ──────────▶    │
      │                                          │
      │ verify(asr_A == asr_B);                  │
      │                                          │
      │ ─── pair.success {fabric_key, head} ─▶   │
      │                                          │
      │            update sync log; bring up RPC channel
      │                                          │
      │ both: emit fabric.peer_introduced fact   │
      │                                          │
      ▼                                          ▼
  bound peer                                 bound peer
```

## 6. Unpair / leave fabric

Two ways:

| Phrase                                      | Effect                                |
|---------------------------------------------|----------------------------------------|
| (on departing device) "Jess, opuść fabric"  | Loud-confirm → wipe key + sync DB + emit `fabric.peer_removed` (signed) so peers stop accepting facts from this device. |
| (on a remaining device) "Jess, wyrzuć telefon z fabric" | Loud-confirm → emit `fabric.peer_removed` for the named peer; once seen, peers stop accepting facts from it. (Removed peer may not have seen the fact yet — if it comes back online it discovers the removal and self-destroys its key.) |

A removed peer **cannot resurrect itself** without going through
pairing again.

## 7. Capabilities at pair time

During pair the new device announces its **kind**:

| Kind          | Default offered capabilities                              |
|---------------|------------------------------------------------------------|
| `appliance`   | `llm.cpu`, `llm.hailo` (if present), `tts.piper`, `mic.array`, `speaker.room`, `storage.bulk` |
| `mobile.ios`  | `llm.apple_intelligence`, `asr.apple_speech`, `tts.avspeech`, `gps`, `cellular_tether`, `calendar`, `contacts` |
| `mobile.android` | `llm.gemini_nano`, `asr.google_speech`, `tts.android`, `gps`, `cellular_tether`, `calendar`, `contacts` |
| `tablet.ios` / `tablet.android` | same as mobile + `screen.large` |
| `wearable.watchos` / `wearable.wearos` | `mic.always_on`, `tts.miniaturised`, `motion_sensor` (M11+) |

The user can disable any capability per peer in
[`13-RESOURCE-SHARING.md`](13-RESOURCE-SHARING.md).

## 8. PL TL;DR

Sparowanie nowego urządzenia z istniejącą Jessicą zajmuje minutę:
albo skanujesz kod QR pokazany na ekranie istniejącego urządzenia,
albo (jeśli pierwsze urządzenie to Pi bez ekranu) **mówisz głośno
sześciowyrazowy kod**, który Pi czyta na głos a Ty powtarzasz w
telefonie. Po sparowaniu nowe urządzenie dostaje kopię klucza
fabric (szyfrowanie end-to-end) i zaczyna synchronizować się z resztą.
Można "wyrzucić" urządzenie z fabric głosem ("Jess, wyrzuć telefon
z fabric"), co unieważnia jego klucz wszędzie.
