# 01 — Architecture

## Goals

1. A single user can interact with `blazen_os` using only voice (microphone +
   speaker). Discovery, recovery, and configuration are all reachable by voice.
2. Every ML step runs locally; the device is usable offline.
3. The system survives a degraded ML path (e.g., LLM hangs) by falling back
   to a rule-based intent matcher and an "I'm sorry, I didn't get that"
   reprompt.
4. SSH is on by default (pubkey-only) as an admin channel, not the default UX.

## Process map

```
                          +----------------------------+
                          |          systemd           |
                          +----------------------------+
                                      |
         +---------+----------+-------+------+----------+----------+
         |         |          |       |      |          |          |
   blazend-     blazend-   blazend- blazend- blazend-  blazend-  blazend-
   audio-in    wake       asr      brain    tts      audio-out  health
   (cpal,RS)   (ort,RS)   (whisp,  (llama,  (piper,   (cpal,RS)  (RS)
                            PY)     PY)      RS)

         +------------+-------------+
         |   blazend-orchestrator   |   <- pipeline supervisor (PY, asyncio)
         +--------------------------+
                      |
                      v
         +--------------------------+
         |  blazend-config (YAML)   |   <- /etc/blazen/*.yaml (shared Python lib)
         +--------------------------+
                      |
                      v
         +--------------------------+
         |  blazend-ssh-recovery    |   <- recovery escalation (SSH already on)
         +--------------------------+

   Legend:  (RS) = Rust,  (PY) = Python.   See docs/14-RUST-PYTHON-SPLIT.md.
```

Each component is a separate systemd unit so:

- a crash in `blazend-asr` does not take down audio capture;
- the watchdog (`blazend-health`) can restart only the failing layer;
- restart loops can have per-component backoff;
- Python and Rust components are isolated by process boundary, not by
  FFI — IPC is the only cross-language contact.

## IPC contract

- **Transport:** Unix-domain sockets under `/run/blazen/`, framed by length-
  prefixed JSON.
- **Topics:** `audio.frame`, `wake.detected`, `vad.start`, `vad.end`,
  `asr.partial`, `asr.final`, `nlu.intent`, `brain.reply`, `tts.frame`,
  `system.event`, `error`.
- **Schema as the cross-language boundary.** Every event is defined by a
  JSON Schema in `configs/_schema/events/<topic>.schema.json`. Rust types
  are generated by `crates/blazend-ipc/build.rs`; Python types by
  `scripts/gen-event-types.py`. CI rejects breaking schema changes that
  don't bump `"v"`. This is what keeps the Python + Rust split sound —
  see [`docs/14-RUST-PYTHON-SPLIT.md`](14-RUST-PYTHON-SPLIT.md) §3.
- **Why not D-Bus?** Too heavy and adds dependency churn on Pi OS Lite.
  We may revisit.
- **Why not gRPC?** Audio streaming wants the smallest possible per-frame
  overhead, and Unix sockets are simpler to mock in tests.

## State

- **Conversation state** lives in `blazend-brain` and is process-local. It is
  flushed on idle (>5 min silence) and on reboot. No persistent identifying
  data, no transcripts on disk, unless `configs/system.yaml: log_transcripts:
  true` (off by default).
- **Configuration state** lives as YAML files in `/etc/blazen/`. Voice-mutable
  options write to `/etc/blazen/voice-overrides.yaml`; SSH-only options write
  to `/etc/blazen/admin.yaml`. See [`07-CONFIGURATION.md`](07-CONFIGURATION.md).
- **System state** (volume, last wake time, last intent, current model) lives
  in `/run/blazen/state.json` and is tmpfs-backed.

## Latency budget (median, end-to-end, Pi 5 16 GB reference)

| Stage                              | Pi 5 CPU | Pi 5 + Hailo-10H |
|------------------------------------|---------:|-----------------:|
| Wake-word detection                | 25 ms    | 25 ms            |
| VAD end-of-utterance               | 150 ms   | 150 ms           |
| ASR (5 s utterance, `medium` multilingual) | 1.6 s | 1.6 s        |
| LLM token first-out (Qwen 2.5 3B)  | 350 ms   | 120 ms           |
| LLM full reply (40 tok)            | 1.5 s    | 600 ms           |
| TTS first-audio                    | 80 ms    | 80 ms            |
| **Total: wake → first TTS sample** | **~2.2 s** | **~1.8 s**     |

> The 16 GB target trades a slightly longer ASR (medium vs small) for
> materially better Polish recognition. If the user prefers snappier
> response over PL quality, switching ASR back to `small` brings the
> total to **~1.3 s CPU / ~0.9 s Hailo** at the cost of ~3% extra WER
> on PL. Both budgets fit comfortably under the 3 s "feels stuck"
> threshold from voice-UX research.

> **Decision (2026-06-11):** Raspberry Pi 5 **16 GB** is the
> reference target for M1..M10 (Pi 5 8 GB is supported with smaller
> models). The CPU path is the contract; the Hailo accelerator path is
> a strict improvement on the same observable behaviour. See
> [`12-ML-ACCELERATOR.md`](12-ML-ACCELERATOR.md).

## Failure modes and recovery

| Failure                             | User experience                              | System action |
|-------------------------------------|----------------------------------------------|---------------|
| Wake word missed                    | Nothing happens. User retries.               | None — design accepts this. |
| ASR returns empty / low confidence  | "I didn't catch that, please repeat."        | Reprompt up to 2x. |
| Intent unknown                      | "I don't know that one yet."                 | Log to `/var/log/blazen/unknown-intents.log` for offline training. |
| LLM hangs (>5 s no first token)     | "One moment..." then "Sorry, I'm stuck."     | Watchdog kills + restarts `blazend-brain`. |
| TTS silent (no audio)               | Beep + LED yellow.                           | Fall back to second TTS voice; if still silent, enable SSH recovery. |
| Audio device gone                   | LED red, no voice.                           | `blazend-health` enables SSH recovery + persists last 100 events for `journalctl`. |
| ML model file corrupt               | "Critical error, recovery mode engaged."     | Boots into read-only recovery image with SSH on. |

## Why these choices

- **Many small processes vs. one monolith:** Easier to mock individual stages
  in component tests (Tier 1) and to swap implementations during R&D (e.g.,
  trying Vosk instead of Whisper) without rebuilding everything. Also the
  prerequisite for splitting Python and Rust by component without FFI.
- **Python orchestrator:** Glue code is short, debuggable on the device, and
  the heavy lifting (faster-whisper / llama-cpp-python) is C/C++ underneath.
- **Rust on the audio + wake + TTS + watchdog path:** these are tight loops
  with strict latency budgets where the GIL would intrude. Rust gives us
  predictable jitter, small binaries, and a trustworthy watchdog.
- **systemd units:** Already there. Adds zero new dependencies and gives us
  free restart policies, journal logs, and resource limits.
