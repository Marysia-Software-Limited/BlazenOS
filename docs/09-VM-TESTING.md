# 09 — VM testing (QEMU)

The reason we can iterate fast on a voice-driven OS is that QEMU lets us
boot the exact image we'd flash to a Pi, with a virtual microphone and
speaker, in CI.

## Target machines

- `qemu-system-aarch64 -M raspi4b` — closest to the Pi 4 we support.
- `qemu-system-aarch64 -M virt -cpu cortex-a72` — faster, less faithful.
  Used for `test-fast`. Not used for any timing assertion.
- `qemu-system-aarch64 -M raspi5b` — added when QEMU upstream supports
  it; until then the Pi 5 reference is **real hardware** for Tier 4 and
  `raspi4b + cpu uplift` for Tier 3 (latency budgets adjusted).

> **Decision (2026-06-11):** until QEMU has first-class Pi 5 support, we
> run Tier 3 against `raspi4b` and adjust the latency budgets accordingly.
> Tier 4 on a physical Pi 5 is the authoritative latency check.

## Image artifacts

`scripts/build-image.sh --format qcow2` produces
`vm-images/blazen_os-<version>.qcow2`. We commit nothing larger than a
few MB; the image is built per CI run from cached `pi-gen` stages.

The image includes both the Python venv (under `/usr/lib/blazen/.venv/`)
and the cross-compiled Rust binaries (under `/usr/lib/blazen/bin/`).
Cross-compilation runs **on the host** before pi-gen — see `make
rust-aarch64` — so the Pi never needs a Rust toolchain.

## Virtual audio

```
            ┌──────────────────────┐
host        │  e2e-runner          │
            │  ┌────────────┐      │
            │  │ piper TTS  │──▶ user_input_NNN.wav
            │  └────────────┘      │
            └──────────┬───────────┘
                       │ alsa-loopback over virtual hub
                       ▼
            ┌──────────────────────┐
QEMU VM     │  /dev/snd/pcmC0D0c   │  <- "microphone"
            │  blazend-audio-in    │
            │  ...                 │
            │  blazend-audio-out   │
            │  /dev/snd/pcmC0D0p   │  -> "speaker"
            └──────────┬───────────┘
                       │ same loopback
                       ▼
            ┌──────────────────────┐
host        │  asr (faster-whisper)│ ◀── speaker_capture_NNN.wav
            │  scenario asserts    │
            └──────────────────────┘
```

Two implementations are supported and selectable:

1. **PipeWire + null-sink + virtual ALSA bridge.** Host has a null sink;
   QEMU is launched with `-audiodev pipewire,id=ad0` and ALSA modules in
   the VM map to it. Recommended for Linux hosts.
2. **PortAudio loopback through file backing.** Simpler, slightly racy.
   We start the WAV play before the wake word and align timestamps. Used
   when running on macOS hosts.

The runner abstracts both behind `tests/tools/audio_backend.py`.

## Launch script

`scripts/run-vm.sh` reads `configs/vm/qemu-raspi.yaml`:

```yaml
machine: raspi4b
cpus: 4
ram_mb: 4096
kernel: /boot/firmware/kernel8.img        # extracted from image build
dtb: /boot/firmware/bcm2711-rpi-4-b.dtb
sd_image: vm-images/blazen_os-0.0.1-dev.qcow2
cmdline: "console=ttyAMA0,115200 root=/dev/mmcblk0p2 rw rootwait"
audio_backend: pipewire                   # or "portaudio-file"
ssh_port_forward: 2222
serial: stdio
display: none
network: usernet                          # SLIRP, with port-forward only
extra_qemu_args: []
```

`run-vm.sh` translates this to a `qemu-system-aarch64` invocation. The
serial console lands in `vm-runs/<ts>/serial.log`.

> **The VM image is a *dev* image.** `make vm-image` builds with
> `--dev`, so `blazen` is a real login user and SSH is enabled at boot
> (see [`06-SSH-BOOTSTRAP.md`](06-SSH-BOOTSTRAP.md) §6). Release images
> (`make pi-image`) are *not* SSH-able — that is the whole point of the
> break-glass contract — so they cannot be used for this boot test.

SSH from the host, using the baked-in dev key:

```bash
ssh -i build/dev-ssh/id_ed25519 -p 2222 blazen@localhost
# serial-console fallback password is 'blazen'
```

`run-vm.sh` prints the exact command (with `-i`) when it boots.

## Hot snapshot

Booting `raspi4b` to a usable state takes ~45 s of host wall time. The
runner snapshots the VM after Tier 2 boot assertions pass:

```bash
qemu-img create -f qcow2 -b vm-images/blazen_os-0.0.1-dev.qcow2 \
                 -F qcow2 vm-runs/<ts>/overlay.qcow2
```

Subsequent scenarios reuse the snapshot and reset between turns by
re-loading from the saved monitor state. End-to-end the per-scenario
cost drops from ~2 min to ~25 s.

## Determinism

ML stages are deterministic given fixed seeds and quantised weights.
The runner sets:

```bash
ASR_BEAM=1
ASR_TEMPERATURE=0.0
LLM_TEMPERATURE=0.0
LLM_TOP_P=1.0
LLM_SEED=0
TTS_LENGTH_SCALE=1.0
```

Override with `--non-deterministic` to run scenarios with model defaults
(useful for spotting brittleness).

## Audio fixtures

Generated by `make audio-fixtures`. For each `user:` line in
`tests/scenarios/*.yaml`:

```
tests/fixtures/audio/<scenario_id>/turn_<NN>_user.wav     # synth (Piper)
tests/fixtures/audio/<scenario_id>/turn_<NN>_assistant.wav # captured at runtime
```

User WAVs are committed only as `.gitkeep`; they are reproducible.

## When the VM and the real Pi disagree

This will happen. The protocol:

1. Reproduce on the real Pi (Tier 4).
2. Capture a 30-second pcap + ALSA + journal dump (`blazen-export-state`).
3. Add the dump to `tests/captures/<date>-<short-desc>/`.
4. If the divergence is QEMU-only, mark the scenario `skip_on: [qemu]`
   and add a fixme link.
5. If the divergence is hardware-only, mark `skip_on: [hardware]` and
   open a milestone item.

We never silently disable assertions.

## Cost / performance notes

- A single Tier 3 run on a beefy dev workstation (Ryzen 7950X, 64 GB)
  takes ~30 min for the whole suite. CI uses the same machine class.
- Memory: peak ~5 GB host RAM for the VM + LLM + ASR running.
- Disk: each `vm-runs/<ts>/` is purged after 7 days by `make clean`.
